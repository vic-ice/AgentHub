# 毕业答辩讲稿 设计解释版

论文：基于AI大模型图书馆智能书籍管理系统设计与实现

主讲人：胡守谦　指导教师：林天亮

本稿对应当前17页PPT，围绕“遇到什么问题、为什么简单做法不够、怎样实现、还存在什么边界”组织。第一部分可以照读，第二部分用于理解与追问。第一部分预计约7～9分钟，具体以计时排练为准；若严格限时6分钟，按第三部分压缩。小标题、阅读提示和技术核验附录不用念。

贯穿案例采用“我读完了《小狗钱钱》，觉得很好看”，避免把“读了”未经澄清就认定为“读完”。以下执行结果属于流程示例，不代表本次实际运行或新截图。

## 一 按17页PPT组织的主讲稿

### 第1页 封面

各位老师好，我是胡守谦，我的论文题目是《基于AI大模型图书馆智能书籍管理系统设计与实现》，指导教师是林天亮老师。

我主要研究的是：用户通过聊天表达阅读需求以后，怎样让这些表达形成真实、持续的业务状态，并用于后续个性化推荐。

### 第2页 目录

下面从课题背景、总体设计、核心功能实现、效果与不足，以及总结五个方面展开，重点解释几个核心设计为什么必要。

### 第3页 课题背景

本项目面向个人阅读，管理想读、在读、已读、弃读，以及评价和备注。

例如用户说：“我读完了《小狗钱钱》，觉得很好看。”用户期待的是书架真的更新，而不仅是一句“记住了”。

所以，我把操作成功的标准放在业务效果上：要求是否真正保存，之后能否查询，并继续影响推荐。

### 第4页 系统总体设计

系统前端使用React和TypeScript，后端使用FastAPI，PostgreSQL保存业务数据。

普通对话由自研Agent Core协调。模型提出结构化动作，后端程序检查并调用业务服务，服务再返回执行回执。

这里的“系统”具体包括动作校验、编译、业务服务和数据库访问程序。这样可以降低“没有执行却回复成功”的风险，但不能保证模型一定理解正确。

### 第5页 多轮对话与上下文处理

用户接着说“把刚才第二本加入书架”，系统需要结合前文确定对象。

因此，会话消息和执行事件会保存下来，模型输入由近期原文和较早内容摘要组成。全放历史容易超过窗口，也可能混入旧状态；全部截断又会失去前文。

摘要与近期原文结合，是为了保留连续理解所需的信息，但摘要仍可能遗漏细节。

### 第6页 三类记忆的职责与存储

临时信息记录本轮正在做什么，例如动作和回执；短期上下文帮助理解同一会话；长期记忆保存跨会话仍有价值的事实。

这样区分，是因为聊过的话可能只是举例或假设，不能全部当成长期偏好。运行时信息也不等于全部丢弃，关键执行事件和业务结果仍会保存。

### 第7页 记忆版本链与当前有效事实

假设我后来把《小狗钱钱》的评价从喜欢改成一般。

直接覆盖能够保存最新值，但会丢失过去的评价；把新旧评价全部交给模型，又容易冲突。

因此，版本链保存变化，当前投影选择仍有效的事实。日常使用当前值，明确询问过去时再读取历史。遗忘则追加失效标记，让事实退出当前使用，属于逻辑遗忘。

### 第8页 智能对话与多事实执行

“读完了，觉得很好看”包含阅读状态和评价两个维度。如果各模块分别理解，可能漏项或者产生不同解释。

所以模型先统一提取结构化事实，例如对象是《小狗钱钱》，状态是已读，评价是喜欢。系统再把同一本书的事实合并，交给阅读服务执行。

一次理解指同一批业务事实不被各模块重复解释，不代表整个请求只有一次模型调用。

### 第9页 书架与长期记忆协同

阅读状态属于用户长期信息，但查询书架要求完整、精确。如果只靠语义召回，漏掉一本书，就可能查询不全或重复推荐。

因此，Shelf保存当前阅读资产，当前投影提供有效记忆，版本链保留变化。它们分别回答“现在有什么”“目前记住什么”和“过去发生过什么”。

### 第10页 图书推荐机制

推荐结合当前需求、长期偏好和阅读信息形成候选，再读取完整书架排重，并利用反馈排序。

当前书架图书由系统硬排除，因为仅靠提示模型不能保证排重完整。已经移出书架的历史图书，通常参与软评分，避免过去一次行为永久限制选择。

这里的动态画像，是推荐时组合的用户信息。当前没有训练专用推荐模型。

### 第11页 阅读状态更新与记忆协同

回到这个例子。阅读服务先查找书架条目，存在就更新，不存在就创建，再派生“已读”和“喜欢”两类记忆版本。

这条Chat写入路径使用同一个数据库会话，提交成功后，根据回执说明结果。之后推荐既能排除这本书，也能利用正向评价。

手动界面同样通过业务服务更新。但部分REST路径先提交书架、再派生记忆，跨事务失败仍需可靠补偿。

### 第12页 深度研究

复杂问题需要的不只是几个搜索结果。例如推荐机器学习教材，还要比较基础要求、实践倾向和配套资源。

因此，深度研究由用户显式开启，给复杂问题分配更多研究资源，也避免普通聊天自动进入高成本流程。它默认不自动读取个性化记忆和书架。

### 第13页 Deep Research研究流程

研究先明确目标和子问题，再并行检索，对来源进行内容检查，维护已知内容、缺口和冲突。

如果只是固定重复搜索，可能得到很多类似排行榜，却没有解决关键判断。所以审查环节根据缺口决定下一步补什么。

例如内容介绍已经足够，但适用基础不清楚，就针对前置要求补充研究。研究围绕问题推进，而不是追求更多轮数。

### 第14页 研究停止与报告生成

研究受轮次和时间预算限制。证据充分可以停止，预算耗尽也必须停止，但两者不能都解释成研究已经充分。

停止后，系统组织判断、证据和未解决问题，再由模型形成报告。报告要解释比较和取舍，让来源支持相应结论。

工具用于增强模型的信息，不能因为没有搜索到某条材料，就把合理分析全部删掉；也不能把模型判断伪装成来源证实的事实。

### 第15页 实现效果与不足

目前已经实现对话更新、分层记忆、版本管理、推荐排重和有界研究。

主要不足是模型仍可能误解意图，现有检查无法覆盖全部语义错误；摘要和记忆选择可能遗漏信息；跨事务同步需要补偿；推荐和研究还缺少系统性效果评测。

后续重点是验证改名、否定、查询误写和同步失败等场景，而不只是增加功能。

### 第16页 总结

这个项目把理解、执行和持续状态连接起来。回执使操作可以核验，版本链让变化可以追溯，书架给精确查询和排重提供依据，用户反馈再影响推荐。

这些设计不能消除全部模型错误，但能够明确事实来源与执行边界，让问题更容易发现和修正。

### 第17页 致谢

我的汇报结束。感谢指导教师的指导，感谢各位老师聆听，恳请批评指正。

## 二 设计思路的展开解释

以下不是连续照读内容，而是每个重点背后的解释。主讲时只讲结论与例子，老师追问时再展开。

### 1 系统执行为什么比让模型直接说成功可靠

用户关心的是状态有没有改变。语言上合理的回答，不能证明数据库发生了变化。因此，模型提议与实际执行之间需要一个明确边界。

当前Agent Core接收结构化决策，校验和编译后交给业务服务。ReadingService中的既定程序决定怎样查找条目、保留未修改字段、记录变化；事务代码负责提交或回滚。最终回复使用执行回执。

这提高的是执行可核验性。合法参数并不能证明语义正确，模型认错书后仍可能更新错对象。因此，不能说程序执行消除了幻觉，需要对象澄清与语义验证共同配合。

### 2 Agent Core为什么属于智能体架构

系统不仅产生文本，还会根据目标选择动作、接收执行反馈，并决定继续、澄清或结束，因此具有智能体特征。

Agent Core是核心编排层，模型提供理解和决策，工具与领域服务提供行动能力，状态和记忆提供连续性。当前属于面向明确业务、回合受限的智能体，不代表能自主完成任意任务。

普通Chat主编排为自研Agent Core。LangChain提供相关模型、消息和工具抽象，LangGraph相关组件涉及研究及Checkpoint、Store基础设施，不能因此把当前普通Chat主链或研究Runner全部等同于LangGraph自动执行。

### 3 一次理解为什么不等于所有动作都原子成功

统一语义结果解决的是解释一致性。同一句话交给多个模块重解，容易漏项和矛盾，因此先提取事实，再由程序分流。

事务一致性是另一个问题。当前Chat阅读写入把书架与阅读记忆派生放在同一个数据库会话，异常时按该会话事务回滚。但其他动作或跨事务路径不能据此承诺全部原子成功，回复仍必须反映真实结果。

### 4 为什么版本链不能替代正确的实体识别

“我的猫叫小花”和“它改名叫咪咪”，必须先判断是同一只猫。如果理解成新增另一只猫，版本链保存得再完整，也只是记录了错误关联。

因此需要区分对象身份与对象属性：实体用于标识同一对象，事实键用于标识对象的某个事实主题，版本链记录这个主题的变化。名称变化不应随意改变对象身份。

当前有实体解析、事实键和当前语义归并等机制，但复杂指代、多对象同名等情形仍需测试和澄清。版本链提供追溯基础，不会自动证明输入真实或语义正确。

### 5 长短期记忆实际怎样提供给模型

短期上下文由会话事件与摘要构成。当前组装器默认最多保留20轮精确对话，采用约12,000 Token估算预算，超出时触发摘要。这些是实现默认值，不代表固定只保存20轮，也不保证所有模型的完整请求严格不超窗口。

长期记忆通过版本存储保存，当前读取采用有效事实投影。普通Chat自动装配默认最多50条当前事实，这一步不按问题执行语义检索。显式记忆搜索工具则可以尝试向量召回并结合版本查询，实际效果受配置和数据影响。

这说明“已经存下来”与“这次准确取出来”仍有区别。长期规模扩大后，检索选择与摘要信息保真都需要评测。

### 6 为什么书架需要独立权威数据

记忆检索通常关注相关性，书架查询关注完整集合。向量相似度不能保证取回全部在读图书，因此不能承担书架排重的唯一依据。

Shelf负责当前集合与字段，Memory保存可复用事实及版本。删除书架条目会影响当前资产与派生当前事实，但不自动抹去历史。普通书架查询读Shelf，明确历史问题再读版本链。

副作用是协同复杂。部分REST修改先提交书架，再派生记忆，当前没有完整事务Outbox补偿。后续可把待同步事件与业务修改同事务保存，由可重试、幂等处理器完成派生。该方案是后续方向，不能说当前已实现。

### 7 推荐的硬约束和软信号为什么分开

当前书架是用户明确的已有资产，“推荐不重复的新书”要求对此硬排重。历史行为是判断信号，用户可能改变想法，不应仅因过去读过就永久禁止。

因此，候选生成以后，当前Shelf图书由程序抑制；其余候选结合偏好和历史反馈进行评分。喜欢一本书可以作为参考，不自动证明用户喜欢该书全部主题或所有同类书。

这里是应用规则与模型能力配合，没有训练专用推荐模型。排重正确、评分可解释，不等于推荐质量已被证明优秀，后续需要相关性、多样性和满意度评价。

### 8 深度研究为什么既需要补证据也需要防止过度压缩

固定多轮搜索容易重复，缺口驱动研究则针对未解决判断分配后续查询。内容检查与证据准入约束哪些材料进入研究，但外部来源错误和模型误判仍可能存在。

另一个风险发生在发布阶段：资料提取与聚合层层压缩，可能把支持比较的细节丢掉，导致最终报告贫乏。PublicationPacket的作用是组织判断依据和未解决问题，不应该成为限制模型综合能力的唯一小型证据清单。

最终验收要检查用户的问题是否覆盖、关键条件是否保留、引用是否支持结论。报告有标题、有引用或者审查通过，只能说明部分检查满足，不能保证研究透彻。

## 四 贯穿案例的数据落点

输入：“我读完了《小狗钱钱》，觉得很好看。”以下是合理语义结果的示意，不是本次模型实测输出。

| 环节 | 形成或使用的信息 | 作用 |
| --- | --- | --- |
| 会话记录 | 用户原话及来源事件 | 延续对话和追溯 |
| Controller理解 | 书名、已读、喜欢 | 形成结构化事实提议 |
| 系统校验与编译 | 合法动作、字段、同书合并结果 | 转换为领域调用 |
| 实体解析 | 对应书籍语义对象 | 关联记忆事实身份 |
| ReadingService | 当前书架已读、喜欢 | 保存权威阅读状态 |
| MemoryWriteGateway | reading.state与reading.feedback | 派生阅读记忆 |
| MemoryVersionStore | 新建、修订或重复结果 | 保留事实演进 |
| 数据库会话 | 正常提交、异常回滚 | 保证该事务持久化边界 |
| 执行回执与发布 | 实际完成的字段 | 回复不超出已执行结果 |
| 下一次推荐 | 完整Shelf与反馈信号 | 排除本书、参考正向评价 |

用户未提供备注，不自动添加，也不清空原备注。目录里没有对应Book记录时，可按标题维护书架，不必为了保存阅读状态强制先联网找书。语义实体与目录Book记录职责不同，不应视为一张表。
